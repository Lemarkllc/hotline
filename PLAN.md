## 3. Backend: архитектура и модель данных

Слои строго по `backend-dev-guidelines`: **routes → controllers (extends BaseController) → services (бизнес-логика, DI через конструктор) → repositories (единственная точка доступа к Prisma)**. Все внешние входные данные — через Zod (`validators/*.schema.ts`). Все async-хендлеры — через `asyncErrorWrapper`. Конфигурация — только через `config/unifiedConfig.ts`, не `process.env` напрямую.

### Prisma-схема (SRS §19)

`users`, `roles`, `user_roles`, `access_requests`, `appeals`, `appeal_assignments`, `appeal_comments`, `appeal_messages`, `appeal_attachments`, `appeal_status_history`, `epics`, `ratings`, `notifications`, `audit_log`, `system_settings`, **`external_contacts`** (см. раздел 6 — заведено сразу, чтобы не мигрировать `appeals` задним числом).

Правила: UUID PK, все даты в UTC, **soft delete** (поле `deletedAt`, физическое удаление запрещено — FR-APP-014), FK, индексы по `status`, `createdAt`, `epicId`, `assigneeId`, **`channel`**; уникальный `publicNumber` (формат зависит от канала — см. раздел 6, для сотрудников `HL-YYYY-NNNNN`), генерируется без привязки к автору/подразделению (FR-APP-011).

Ключевое поле модели `Appeal`: `originalText` (immutable после отправки) и отдельно `workingEdit` (нейтральная рабочая редакция HRD) — никогда не перезаписывают друг друга (SRS §7.3, FR-CONF-006). Поле `channel: EMPLOYEE | CUSTOMER` — дискриминатор с первого дня (раздел 6), для MVP всегда `EMPLOYEE`.

### Разграничение доступа

RBAC как явный набор permission-строк (SRS §21): `appeal.read_all`, `appeal.read_assigned`, `appeal.read_author`, `appeal.assign`, `appeal.close`, `report.read`, `report.export`, `user.manage`, `audit.read`. Проверка — в middleware `rbac.ts`, до контроллера. Permission-строки channel-agnostic; фактический доступ к каналу — через `user_channel_access` (раздел 6), для MVP каждому HRD/менеджеру/админу автоматически выдаётся доступ к каналу `EMPLOYEE`.

**Критический инвариант**: сокрытие автора конфиденциального обращения реализуется в `services/appealService.ts` на уровне сериализации ответа (никогда — только в UI). Каждый просмотр автора конфиденциального обращения пишется в `audit_log` через `auditService` (FR-CONF-005/FR-PRV-005).

### Auth

- **Web**: email+пароль (Argon2id, ≥12 симв.), JWT access+refresh, обязательный TOTP 2FA для HRD/Администратора (SRS §21). Аккаунты создаёт Администратор — отдельная регистрация от бота (SRS §4.1: "Для Web панели регистрация отдельная").
- **Bot↔API**: bot-сервис аутентифицируется к API service-token'ом (`BOT_SERVICE_TOKEN` из env), передаёт `telegramId` как идентификатор конечного пользователя. Endpoint `POST /auth/telegram` создаёт/находит `access_request`/`user` и возвращает статус.

### API-эндпоинты (SRS §20, `/api/v1`)

Полный список из ТЗ реализуется как реальные роуты; в Фазе 1–2 — полностью рабочие (auth, users approve/reject/block, appeals CRUD/status/comments/attachments/assign/rating), в Фазе 3 — отчёты и экспорт.

## 4. Telegram-бот сотрудников (`apps/bot-employee`, MVP): архитектура

`grammy` + `conversations` для многошаговых сценариев с сохранением состояния (нужно для восстановления сценария после рестарта — FR §15 UX, черновики 24ч — FR-DRF-002). Redis — session storage бота. HTTP-клиент к API, retry доставки уведомлений и session-middleware живут в переиспользуемом `packages/bot-core` (см. раздел 6 — второй, клиентский бот использует то же ядро).

Сценарии (SRS §35): первый запуск → ФИО → правила конфиденциальности → заявка → ожидание подтверждения (`registration.ts`); создание обращения: тип → режим → наводящие вопросы (пропускаемые) → текст → вложения (до 10, счётчик) → предпросмотр → отправка → номер (`newAppeal.ts`); «Мои обращения» с пагинацией кнопками (`myAppeals.ts`); доставка уточнений от HRD и приём ответа автора (`clarification.ts`).

Бот **не хранит бизнес-данные сам** — всё идёт через API-клиент из `bot-core` в backend API (архитектурная схема §24: `BOT --> API --> DB`). Локально в Redis бот держит только состояние диалога/черновика до отправки.

## 5. Web-панель: дизайн-система и структура

### Дизайн-система (через `ui-ux-pro-max`, адаптировано под HR/enterprise-контекст)

Запрос дал профиль "Enterprise Gateway / Soft UI Evolution" с тёмной навигационной палитрой и шрифтом Fira Code для заголовков — это слишком "разработческий" тон для инструмента, которым каждый день пользуются HRD и мастера цехов, часто без технического бэкграунда. Адаптирую:

Обоснование по методологии `frontend-design`: это внутренний инструмент доверия и конфиденциальности, а не продающая страница — "рискованный" визуальный акцент здесь неуместен. Единственный сознательный акцент — фиолетовый маркер конфиденциальности, который проходит через весь UI (бейджи, kanban-карточки, детальная карточка) как визуальный сигнал "здесь данные автора защищены".

Соответствие чек-листу `ui-ux-pro-max`: SVG-иконки (lucide-react) без эмодзи в качестве иконок, контраст ≥4.5:1, видимый focus-ring, `prefers-reduced-motion`, touch-target ≥44px, семантические цвет-токены (не хардкод hex в компонентах — через CSS-переменные/Tailwind theme).

## 6. Масштабирование: канал клиентских обращений

Требование заказчика: после MVP — второй источник обращений, клиенты компании (жалобы/отзывы о заказах, опыте работы), через **отдельного Telegram-бота**, но с **общей web-панелью** и **отдельным Kanban**.

### Рассмотренные варианты

1. **Полностью отдельный домен** (своя таблица `customer_feedback`, свой набор статусов, отдельный кусок API) — чище с точки зрения границ контекста, но дублирует весь жизненный цикл (статусы, вложения, комментарии, рейтинг, уведомления, аудит), который у клиентского обращения устроен ровно так же, как у обращения сотрудника: подано → рассматривается → в работе → закрыто → оценка. Двойная поддержка одной и той же механики ради разных источников — неоправданные расходы на сопровождение.
2. **Мультитенантность по предприятию** (SRS §30, roadmap 2.0 "несколько предприятий") — не то же самое измерение: там речь про изоляцию разных юрлиц/компаний, здесь — про разные *аудитории внутри одной* компании. Смешивать эти два измерения в одном флаге не стоит.
3. **Единая сущность `Appeal` с дискриминатором `channel`** (выбрано) — статусная машина, вложения, комментарии, рейтинги, уведомления, аудит переиспользуются как есть; расходятся только: кто автор, какой набор типов/эпиков, какая семантика конфиденциальности, кто видит.

### Модель данных

```
enum Channel { EMPLOYEE, CUSTOMER }

model Appeal {
  channel            Channel
  publicNumber       String   @unique   // HL-YYYY-NNNNN (EMPLOYEE) / CF-YYYY-NNNNN (CUSTOMER)
  authorUserId       String?            // задан при channel = EMPLOYEE (FK -> User)
  externalContactId  String?            // задан при channel = CUSTOMER (FK -> ExternalContact)
  epicId             String?            // FK -> Epic, где Epic.channel === Appeal.channel
  ...                                   // status/type/mode/attachments/comments/rating — без изменений
}

model ExternalContact {          // "клиент", не сотрудник — без approval-флоу access_requests
  id           String   @id @default(uuid())
  telegramId   BigInt
  fullName     String?
  phone        String?
  orderNumber  String?            // привязка к заказу, если указан
  consentAt    DateTime?          // согласие на обработку данных — обязательно для внешних лиц
  appeals      Appeal[]
}
```

`Epic` получает поле `channel` — справочники эпиков/тем у сотрудников ("Условия труда", "Оборудование"...) и у клиентов ("Качество заказа", "Доставка", "Сервис"...) — разные списки, тот же механизм администрирования (SRS §34.8). Так же и с типом обращения: набор типов для канала `CUSTOMER` не обязан совпадать с пятью типами SRS §6.1 (там были заточены под сотрудника) — заводится отдельным справочником по тому же принципу.

Автор моделируется как **union**: `User` (сотрудник, с approval-флоу через `access_requests`) либо `ExternalContact` (клиент, без approval — старт бота сразу доступен после согласия на обработку данных, см. ниже). Общей таблицы "автор" нет намеренно — у этих двух сущностей разные жизненные циклы и разные требования к хранению (сотрудник — внутренний субъект данных с ролями, клиент — внешний субъект с согласием на обработку).

### RBAC и разделение аудиторий

Ключевой риск — не допустить, чтобы человек, которому дали доступ к клиентским обращениям, автоматически получил доступ к внутренним (потенциально куда более чувствительным) обращениям сотрудников, и наоборот. Решение: доступ к permission всегда **дополнительно скоуплен по каналу** через `user_channel_access(userId, channel)`. Роль (HRD/Менеджер/Администратор) даёт *набор permission*, `user_channel_access` даёт *к какому каналу они применяются*.

**Решено (30.07.2026):** новая роль называется **«Продажи»** (`SALES` в `RoleName`), не «Менеджер поддержки клиентов» — переиспользует ровно permission-набор HRD (`appeal.read_all`, `appeal.read_author`, `appeal.assign`, `appeal.close`, `report.read`, `report.export`), но со скоупом `user_channel_access(CUSTOMER)`, а не `EMPLOYEE`. Продажи единолично ведут канал `CUSTOMER` целиком: видят все клиентские обращения, классифицируют по эпику/типу, назначают (если появится второй исполнитель в канале), закрывают, видят свой Dashboard/Отчёты, отфильтрованные по `channel=CUSTOMER`. Второй, более узкой роли (аналог Менеджера) в этой фазе нет — не нужна, пока весь канал ведёт один отдел. По умолчанию HRD-сотрудников (канал `EMPLOYEE`) в канал `CUSTOMER` никто не добавляет автоматически, и наоборот — роль `SALES` не получает `user_channel_access(EMPLOYEE)` по умолчанию (см. допущение №8 раздела 9, теперь симметрично применяется и к `SALES`).

**Найден и закрыт пробел (10.08.2026):** до этой даты в приложении не было НИ ОДНОГО экрана/эндпоинта для управления `user_channel_access` — единственный способ выдать/забрать канал был прямой SQL. Из-за этого двум реальным аккаунтам роли `SALES` на проде вручную выставили `EMPLOYEE` вместо `CUSTOMER` (перепутали "сотрудник компании" с "канал EMPLOYEE = обращения от сотрудников") — они видели чужую очередь HRD вместо своих клиентских обращений. Данные поправлены, и добавлен полноценный UI (см. `UsersPage.tsx` → диалог редактирования пользователя, чекбоксы каналов) поверх нового эндпоинта `PATCH /users/:id/channels` (`user.manage`) — теперь это делается через приложение, не руками в БД.

**Аудит всех существующих пользователей проведён (10.08.2026):** сверены роль↔канал всех аккаунтов с назначенной ролью на проде. Расхождений, кроме двух уже найденных и поправленных `SALES`-аккаунтов, не обнаружено — HRD/Administrator/Manager везде `EMPLOYEE`, SALES везде `CUSTOMER`. (Роль `EMPLOYEE` в `RoleName` — обычные сотрудники, подающие обращения через бота — это совпадение имени с каналом `EMPLOYEE`, не путаница: им канал `EMPLOYEE` и положен.) Пробел закрыт полностью.

### Конфиденциальность для канала CUSTOMER (решено: да, тот же механизм, что у сотрудников)

`Appeal.mode` (`OPEN`/`CONFIDENTIAL`) работает одинаково для обоих каналов — никакого отдельного enum не требуется. В режиме `CONFIDENTIAL` поля `ExternalContact` (ФИО, телефон, telegramId, номер заказа) скрываются от роли «Продажи» точно так же, как данные сотрудника скрываются от обычного Менеджера (FR-PRV-002/003) — сериализация на уровне `appealService`, а не UI. Кто видит контакт клиента в конфиденциальном режиме — тот, у кого есть `appeal.read_author` **и** `user_channel_access(CUSTOMER)` (то есть роль «Продажи» по определению — она получает `appeal.read_author` в наборе прав, см. раздел RBAC выше). Каждый такой просмотр журналируется в `audit_log`, как и для сотрудников (FR-CONF-005/FR-PRV-005). Рабочая редакция (`workingEdit`) переиспользуется тем же образом: ответственный может обезличить текст перед передачей исполнителю, не раскрывая, кто из клиентов и по какому заказу обратился.

Практическое следствие, о котором стоит помнить: скрытие телефона/номера заказа может затруднить решение проблемы клиента (менеджеру нечем с ним связаться) — то же компромиссное решение уже принято в SRS для сотрудников (§29, риск "недоверие к конфиденциальности") и снимается тем же способом — рабочей редакцией с достаточной информацией для действия, без раскрытия личности.

### Согласие на обработку персональных данных (решено: да, отдельное от политики сотрудников)

`ExternalContact` получает `consentAt: DateTime` и `consentVersion: String` (версия текста, на который согласился клиент — чтобы отследить, на какую редакцию политики опирается согласие при её будущих изменениях). Бот `bot-customer` **не даёт создать обращение до явного согласия** — отдельный шаг `consent.ts` в самом начале диалога, до сбора ФИО/контакта. Текст согласия отличается от корпоративной политики конфиденциальности для сотрудников (SRS §5): сотрудник — внутренний субъект в рамках трудовых отношений, клиент — внешний субъект, поэтому нужна отдельная формулировка про цели обработки (обратная связь по заказу/сервису), состав данных, срок хранения и право отзыва согласия. Точный юридический текст — вне зоны ответственности разработки, но поле для его версии в модели уже заложено.

### Web-панель

Общая оболочка (layout/auth/дизайн-система без изменений), в навигации — переключатель канала (Сотрудники / Клиенты) для пользователей, у которых есть доступ к обоим. **Kanban, Реестр и Dashboard — те же компоненты**, параметризованные фильтром `channel` (ровно то, что просил заказчик: "сортировать в отдельной канбан" — реализуется как отдельная доска per channel, а не отдельный экран с нуля). Отчёты дополнительно получают `channel` как ещё одно измерение фильтрации наравне с существующими (период/статус/тип/эпик).

### Боты

Два отдельных Telegram-бота, каждый — свой токен, свой процесс, независимый деплой/масштабирование (клиентский бот потенциально на порядки больше по нагрузке, чем внутренний на 200 сотрудников) — `apps/bot-employee` и `apps/bot-customer`. Общая логика (HTTP-клиент к API, retry доставки уведомлений, session-middleware, конвенции клавиатур) вынесена в `packages/bot-core`, чтобы не дублировать. Разный контент: у клиентского бота нет шага "ожидание подтверждения администратором" — это принципиально другой (упрощённый) flow.

### Нумерация

Публичный номер обращения получает **свой префикс на канал** (`HL-` для сотрудников, `CF-` — customer feedback — для клиентов) — не идентифицирует ни автора, ни подразделение (требование FR-APP-011 сохраняется), но сразу понятно из номера, какого рода обращение, что упрощает коммуникацию между HRD/CX и клиентом/сотрудником.

### Флоу `bot-customer` (решено 30.07.2026)

Сильно проще, чем у сотрудников — не пошаговый мастер с наводящими вопросами SRS §35, а короткий флоу:

1. `consent.ts` — согласие на обработку данных (см. выше), блокирующий шаг, без него дальше нельзя.
2. **Мягкий** квалифицирующий вопрос "Покупали ли вы у нас / обращались ли раньше?" — это ПЕРВЫЙ наводящий вопрос, ответ идёт в текст обращения, как и у сотрудников; бот НЕ блокирует создание обращения при ответе "нет". Реализуется тем же паттерном `guidedQuestions.ts`, что уже есть в `bot-employee`, просто с другим (более коротким) набором вопросов.
3. Выбор типа: **только два** — `COMPLAINT` (жалоба) и `GRATITUDE` (благодарность). Отдельный `CUSTOMER_APPEAL_TYPES` в `packages/shared` (не пересекается с пятью типами SRS §6.1 — см. заметку выше про `Appeal.type` как `String`, а не enum, ровно для этого случая), Zod-схема создания обращения для канала `CUSTOMER` валидирует по этому короткому списку.
4. Текст жалобы/благодарности — свободным текстом, без развёрнутого guided-flow сотрудника (SRS-флоу писался под другой контекст, здесь достаточно 1-2 коротких вопросов).
5. Вложения — тот же механизм (draft-attachments), без изменений.
6. После закрытия обращения — **два отдельных вопроса по 5-балльной шкале** вместо одного (см. ниже), а не переиспользование сотруднической `ratingKeyboard(appealId)` как есть.

### Оценка клиента — NPS-style, два вопроса (решено 30.07.2026)

Вместо одного `Rating.score` (как у сотрудников — "насколько результат решил вопрос") клиентский флоу задаёт два независимых вопроса по 1-5, оба обязательны при закрытии `CUSTOMER`-обращения:

- **Рекомендовали бы вы нас?** (`Rating.wouldRecommendScore`)
- **Обратитесь ли вы к нам снова?** (`Rating.wouldReturnScore`)

Модель `Rating` получает эти два новых nullable-поля (`Int?`) вместо второй таблицы — избыточно заводить отдельную сущность ради двух чисел, привязанных к тому же `appealId`. Для канала `EMPLOYEE` они остаются `null`, `score`/`comment` используются как раньше без изменений. Для канала `CUSTOMER` — наоборот: `score`/`comment` не используются (бот не задаёт "насколько решило вопрос" клиенту), обязательны оба новых поля. `notificationService.notifyLowRating` при необходимости расширяется — что считать "низкой оценкой" для двух чисел, а не одного, требует отдельного решения при реализации (например, любое поле ≤2).

### PWA для web-панели персонала (решено 30.07.2026)

`apps/web` (HRD/Manager/Administrator/**Продажи**) становится устанавливаемым PWA — `manifest.json` + расширение уже существующего `public/sw.js` (сейчас только под web push) под офлайн-оболочку (кэш статики, экран "нет соединения" вместо белого экрана). Это про панель персонала, не про клиентский канал — клиент как обращался через `bot-customer` (Telegram), так и обращается, второе клиентское веб-приложение параллельно с ботом не обсуждалось и не планируется.

### Открытые вопросы по каналу CUSTOMER (требуют вашего решения, аналогично SRS §42)

Решено (17.07.2026): режим конфиденциальности — тот же механизм, что и у сотрудников; согласие на обработку персональных данных клиента — обязательно, отдельным текстом от политики сотрудников. Решено (30.07.2026): роль называется «Продажи» и ведёт канал `CUSTOMER` целиком, см. выше; флоу бота, типы обращений и двухвопросная оценка — см. подразделы выше. Остаётся открытым:

- Нужна ли интеграция с системой заказов для валидации `orderNumber`, или в MVP этого канала поле остаётся свободным текстом.

Реализация канала `CUSTOMER` — отдельная фаза (Фаза 7, см. раздел 8) **после** сдачи MVP по сотрудникам; в текущей фазе 0 закладывается только `channel`-дискриминатор в схеме, чтобы не потребовалась миграция данных задним числом.

## 10. Модуль «Отпуска / Отсутствия / Командировки» (решено 04.09.2026, через `/grill-me`)

Кадровый модуль, изначально запрошенный как «добавить в бота меню Отпуск» + «опоздания» (раздел не пересекается с каналом `CUSTOMER` из раздела 6 — это чисто внутренняя, `EMPLOYEE`-сторона). Первая итерация (см. git-историю) реализовала «Отпуск» как отдельную сущность `VacationRequest` и «опоздания» как новый тип обращения `TIME_OFF` («Отпроситься») внутри `Appeal`. После разговора с HRD решение пересмотрено: «Отпроситься» переносится из `Appeal` в тот же раздел, что и «Отпуск», под новым именем «Отсутствие», и туда же добавляется третья сущность — «Командировка». Ниже — согласованный через `/grill-me` план для всех трёх.

### Архитектура и модель данных

**Три отдельные сущности**, не один `TimeOffRequest` с полем-дискриминатором: `VacationRequest` (уже реализован), `AbsenceRequest` (новый, замена `TIME_OFF`), `BusinessTripRequest` (новый). Причина разделения — у каждой свой набор специфичных полей (баланс/оплата у отпуска, транспорт/отель у командировки), общий у всех только жизненный цикл (`PENDING → APPROVED/REJECTED`, согласует HRD) и общий раздел в UI — этого недостаточно, чтобы оправдывать одну «широкую» таблицу с кучей nullable-колонок ради экономии на роутах/контроллерах.

`TIME_OFF` **полностью убирается** из `EMPLOYEE_APPEAL_TYPES` и всей связанной логики бота/веба (`guidedQuestions.ts`, ветка в `newAppeal.ts`, `conversations/timeOff.ts` — переиспользуется как основа для нового `conversations/absence.ts`, не сохраняется как отдельный флоу). Уже созданные тестовые обращения этого типа (`HL-2026-00011` и ранее удалённые) — тестовые данные, миграция в новую таблицу не делается, остаются как есть в реестре «Обращения» (исторические записи).

```prisma
enum VacationBalanceStatus { PENDING APPROVED REJECTED }  // общий для трёх сущностей ниже

model VacationRequest {

  // comment, status, decidedById, decidedAt, decisionReason
  // + новое:
  paid  Boolean   // true = оплачиваемый (проверяется по балансу), false = за свой счёт (без лимита)
}

model AbsenceRequest {
  id             String   @id @default(uuid())
  publicNumber   String   @unique          // отдельный префикс/sequence-ключ, см. ниже

  date           DateTime
  timeFrom       String?                   // null при fullDay = true
  timeTo         String?
  fullDay        Boolean

  transport      String                    // "CAR" | "PLANE" | "TRAIN" | "OTHER"
  transportOther String?                   // уточнение текстом, если transport = "OTHER"
  hotelNeeded    Boolean
  status         VacationBalanceStatus @default(PENDING)
  decidedById    String?
  decidedAt      DateTime?
  decisionReason String?
  createdAt      DateTime @default(now())
  updatedAt      DateTime @updatedAt
}

model User {
  // ...существующие поля

}

model VacationBalance {

  startingBalance Float    // остаток на дату asOfDate, вручную из кадровых данных

}
```

`EmploymentPeriod` (история переприёмов) сознательно **не заводится** — нет сигнала, что сценарий «уволили → приняли обратно» актуален, ни сейчас, ни в описанном ниже будущем онбординге. Если понадобится — добавляется отдельной миграцией, не трогая уже работающую логику баланса.

### Формула расчёта остатка отпуска (SRS не покрывает — новое требование заказчика)

Модуль расчёта — самое рискованное место всей фичи (реальные деньги/дни реальных людей), поэтому логика вынесена в отдельный чистый модуль (`apps/api/src/utils/vacationBalance.ts` или аналог), без побочных эффектов, чтобы его можно было мутационно тестировать (см. ниже).

1. **Начисление**: 2.33 дня за каждый «цикл» — период, отсчитываемый от даты-годовщины приёма на работу (`hireDate`), а не от календарного месяца. Цикл засчитывается **целиком**, если с его начала прошло **≥15 календарных дней** (правило ТК РФ: отработал больше половины месяца — месяц засчитан целиком; меньше половины — не засчитан). Порог зафиксирован как **ровно +15 дней** от даты начала цикла — не пропорционально фактической длине месяца (28–31 день) — сознательное упрощение ради простоты реализации и тестирования, разница с точным расчётом не больше 1 дня в редких случаях.
2. **Итоговый баланс** = `startingBalance` (из `VacationBalance`, ручной ввод) `+ 2.33 × количество_циклов_заработанных_после_asOfDate − сумма_одобренных_дней_VacationRequest{paid: true}_после_asOfDate`.
3. **Округление**: нестандартное правило по требованию заказчика — дробная часть `< 0.6` округляется **вниз**, `≥ 0.6` — **вверх** (не math-стандартное округление по 0.5). Округление применяется **один раз**, к точному дробному накоплению, и получившееся целое число — это и есть то, что сравнивается с запрошенными днями отпуска в боте, и то, что показывается пользователю (нет отдельного «дисплейного» округления и отдельного «расчётного» дробного значения — только одно целое число после округления).
4. **Оплачиваемый отпуск** (`paid: true`) — бот не даёт выбрать диапазон дат, превышающий округлённый баланс. **За свой счёт** (`paid: false`) — без ограничений в коде, HRD решает при одобрении/отклонении (обязательная причина отказа уже реализована).

Граничные случаи, обязательные для тест-сьюта (обычного и мутационного): ровно 15-й/14-й день цикла; ровно `0.60`/`0.599999` при округлении; дата приёма 29–31 числа месяца, где следующий месяц короче (тот же класс бага, что уже был пойман и закрыт в `parseDate` для дат отпуска — сверка компонентов даты после `Date.UTC`, а не доверие тихому автоперекату JS `Date`).

### Стартовые данные

Реальные `hireDate` + `startingBalance`/`asOfDate` по всем текущим сотрудникам — предоставляются заказчиком **отдельным файлом при заливке на прод** (разовый импорт-скрипт напрямую через Prisma, без общего UI импорта). До этого момента — тестовые фикстуры для локальной разработки. Пока данные не залиты, баланс для реального сотрудника не должен показываться как «0» или любое другое правдоподобно выглядящее число — нужно явное UI-состояние «баланс не настроен», отличимое от «баланс = 0 дней».

Для операционного использования **после** разового импорта (HRD заводит нового сотрудника до того, как заработает будущий бот-онбординг из раздела ниже) — `hireDate` и `startingBalance`/`asOfDate` становятся обычными редактируемыми полями в форме создания/редактирования пользователя на `UsersPage`.

### RBAC

Одно общее право `vacation.manage` (уже существует) гейтит все три сущности и весь раздел — не заводим `absence.manage`/`business_trip.manage` отдельно. Согласующий везде один — HRD; нет сигнала, что кто-то другой когда-либо будет одобрять что-то из этого раздела.

### Веб

Один пункт меню «Отпуска» (как сейчас) → страница с тремя вкладками: **Отпуска** / **Отсутствия** / **Командировки** (множественное число — тот же паттерн именования, что «Обращения»/«Заявки»/«Пользователи»). Каждая вкладка — свой реестр (своя таблица, свой набор колонок под специфичные поля сущности), общий паттерн одобрения/отклонения (кнопка «Одобрить», `ReasonDialog` для «Отклонить» с обязательной причиной — переиспользуется как есть).

### Бот

Три отдельные кнопки в главном меню, на замену единственной нынешней «Отпуск»: **«Отпуск»**, **«Отсутствие»**, **«Командировка»** (единственное число — называют действие, не список).

- **«Отпуск»**: кнопки «Оплачиваемый»/«За свой счёт» → дата с/по (валидация диапазона против баланса только для оплачиваемого) → кнопка «Узнать количество дней отпуска» **внутри диалога**, рядом с вводом дат (не отдельный пункт меню) → отправка на согласование. После одобрения — единственный из трёх типов, где в уведомлении сотруднику **дополнительно** сказано «принесите копию заявления в отдел HR» (ТК РФ требует письменное заявление именно для отпуска; у «Отсутствия»/«Командировки» — обычное короткое уведомление об одобрении/отклонении).
- **«Отсутствие»** (бывшее «Отпроситься»): сохраняет уже реализованный сбор данных — дата → время (диапазон или «Весь день») → необязательная причина → предпросмотр → отправка. Меняется только целевая сущность (`AbsenceRequest` вместо `Appeal{type: TIME_OFF}`) и модель решения — теперь формальный `PENDING → APPROVED/REJECTED`, HRD явно одобряет/отклоняет (было — просто попадало в общий статус-флоу обращений без явного решения).
- **«Командировка»** (новая): дата с/по → цель поездки (**обязательный** текст — без неё HRD согласовывает вслепую) → транспорт (Авто/Самолёт/Поезд/Другое, при «Другое» — уточнение текстом) → нужен ли отель (да/нет) → предпросмотр → отправка на согласование.

### Тестирование

`vitest` unit-тесты как обычно на все три сервиса/репозитория, плюс **Stryker Mutator** — узко, **только** на модуль формулы расчёта баланса (`vacationBalance.ts`), не на весь `apps/api`. Обоснование узкого охвата: это единственное место, где тонкая ошибка на границе (`>` вместо `>=` на пороге 15 дней или 0.6) даёт правдоподобную, но неверную цифру, которую не поймает ни код-ревью, ни обычное юнит-покрытие «по строкам»; остальной код (CRUD/роуты) — либо падает явно при ошибке, либо ловится живым QA перед каждым коммитом, как и весь остальной проект.

### Связь с будущим онбордингом (контекст, не задача этой фазы)

Планируется полноценный онбординг через бота: приветствие с правилами/ценностями → согласие на обработку данных → анкета (ФИО, подразделение из списка, должность из списка по подразделению, график работы) → фотопортрет для регистрации в собственной FaceAI СКУД-системе (на терминалах Hikvision) → одобрение HRD создаёт пропуск в FaceAI; увольнение и отпуск/отсутствие также должны будут отмечаться в FaceAI (сейчас, до реализации интеграции, всё делается там вручную). Это отдельная будущая задача, но она уже учтена в сегодняшних архитектурных решениях: `User.hireDate` — то же самое поле, которое future-флоу онбординга будет заполнять автоматически при одобрении анкеты (вместо сегодняшнего ручного ввода HRD), а точки `approve()` у `VacationRequest`/`AbsenceRequest`/`userService.blockUser()` — естественные места для будущих вызовов интеграции с FaceAI, когда она появится. Никакой перестройки сегодняшнего кода эта будущая фаза не потребует.
