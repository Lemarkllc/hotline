# Design

## Context

Мотивация — см. proposal.md. Требования — `specs/vpn-subscription/spec.md`.

Что есть сейчас (проверено вживую на панели `hpl.lemarkllc.ru`, 2026-09-30):

- Сотрудник получает ссылку на наш домен (`/api/v1/vpn/sub/:subId`), `vpnService.proxySubscription` проксирует её на панель (`config.vpn.subBaseUrl + subId`), пробрасывая `X-HWID` и `User-Agent`, подменяет `Profile-Title` и `Routing`.
- Панель 3X-UI — та же сборка, что у VPNbyte: единая модель клиентов (`/panel/api/clients/add` с `inboundIds`), у клиента `limitHwid`, ключи WireGuard (`privateKey/publicKey`) и `tunnelAllowedIPs` по inbound'ам. AmneziaWG-inbound `915` («AMN», порт 44034) уже поднят, привязан пока к одному клиенту.
- `subJsonAutoDetect: true`, `subJsonUserAgentRegex: (?i)^(happ|incy)([ /]|$)` — один и тот же путь `/sub/` отдаёт Happ/INCY JSON (Xray-конфиги), остальным — сырой base64-список ссылок. AmneziaWG в JSON не попадает, в сыром списке — как `vpn://<base64url conf>`.
- `subIncyEnableRouting: false` — INCY Routing-профиль не получает.
- API панели не отдаёт список зарегистрированных HWID клиента (`/clients/hwids/*` → 404); `incy_merge.py` берёт его прямо из SQLite панели — нам это недоступно (API на другом сервере).
- `vpnGeoDataService` уже скачивает и кеширует на 24 ч Loyalsoldier `geoip.dat` (16,6 МБ), в нём есть категория `RU`.

## Goals / Non-Goals

**Goals:**
- Перенести в наш прокси логику `incy_merge.py`, которая относится к AmneziaWG: сборку AWG-серверов для INCY, клиентский split-routing через `AllowedIPs`, слоты по HWID.
- Никакого доступа к диску или БД панели — только её HTTP API и эндпоинты подписки.
- Никаких изменений для Happ и прочих клиентов.

**Non-Goals:**
- Правка названий Xray-серверов («Чехия - 1.76TB» → «Чехия») из `incy_merge.py` — у нас нет таких названий.
- Больше двух слотов: лимит устройств у нас фиксирован (`VPN_PROFILE_HWID_LIMIT = 2`); код считает слоты от лимита, но вспомогательный клиент создаём только для слота 2.
- Раздельная маршрутизация для Xray в коде — она уже делается Routing-профилем панели; для INCY это включение настройки на панели.
- Доменные исключения (`mail.lemarkllc.ru` через прокси и т.п.) в AmneziaWG — `AllowedIPs` понимает только IP.

## Decisions

### 1. Логика в Node-прокси, а не `incy_merge.py` на сервере панели
Прокси уже стоит между приложением и панелью, уже знает профиль сотрудника и уже имеет кеш `geoip.dat`. Альтернатива — развернуть `incy_merge.py` рядом с панелью и направить `subBaseUrl` на него — отвергнута: чужой код без тестов, прямые чтения SQLite панели (ломается при обновлении панели), вторая точка обработки подписки помимо нашего прокси, и отзыв при увольнении всё равно пришлось бы делать у нас.

### 2. AmneziaWG-конфиги берём из сырой подписки панели, а не собираем сами
Для слота N запрашиваем `/sub/<subId слота>` с нейтральным User-Agent (не совпадает с `subJsonUserAgentRegex`, например `HotLineMergeFetcher/1.0`) — панель отдаёт сырой список, из него берём строки `vpn://`, раскодируем base64url, проверяем, что это WireGuard с маркерами AmneziaWG (`Jc`, `S1`, `H1`, `I1`, `HeaderProtectionKey`…). Для слота 1 пробрасываем `X-HWID` (основной клиент под лимитом устройств), для слота 2 — без него.
Альтернатива — собрать `[Interface]/[Peer]` из API-данных клиента и inbound'а — отвергнута: пришлось бы повторять генерацию панели (endpoint, параметры обфускации `I1…`, DNS, MTU), и любое обновление панели молча расходилось бы с нашей копией.

### 3. Split-routing считаем сами из `geoip.dat`, без новых зависимостей
Чистые функции (без I/O, покрываются unit-тестами):
- минимальный protobuf-ридер (`GeoIPList.entry=1`, `GeoIP.country_code=1`, `GeoIP.cidr=2`, `CIDR.ip=1`, `CIDR.prefix=2`) — достаёт сети категории `RU`;
- расширение IPv4 длиннее /19 до /19, слияние, дополнение до всего диапазона (интервалы на `bigint`), добавление сетей, которые должны быть в туннеле, и повторное слияние;
- подстановка в конфиг: ровно одна строка `AllowedIPs`, иначе ошибка.
Результат кешируется в памяти по отметке времени загрузки `geoip.dat` из `vpnGeoDataService` — пересчёт раз в обновление файла, не на каждый запрос. Библиотеки CIDR (`ip-cidr`, `netmask`) не берём: нужны только слияние и дополнение (~100 строк), а тесты на граничные случаи всё равно пишем свои.

Константы (в `config/vpnConfig.ts`, с комментарием-источником):
- напрямую: локальные/служебные сети (как в `incy_merge.py`) + корпоративные адреса из текущего Routing-профиля панели (`DirectIp`: `192.168.37.0/24`, `62.210.70.252/32`);
- всегда в туннеле: сети Telegram + `ProxyIp` Routing-профиля (`62.210.70.253/32`);
- префикс укрупнения `/19`, предел 12 000 маршрутов.

### 4. Слоты храним у себя, «доступ» устройства подтверждает панель
Нет API со списком HWID, поэтому правило такое: устройство получает слот, только если панель ответила на запрос основной подписки с его `X-HWID` успешно — лимит устройств по-прежнему решает панель. Новая Prisma-модель `VpnAwgSlot` (`profileId`, `slot`, `hwidHash` SHA-256, `assignedAt`, `lastSeenAt`; уникальность `(profileId, slot)` и `(profileId, hwidHash)`). Алгоритм в транзакции:
1. есть строка с этим `hwidHash` → обновить `lastSeenAt`, вернуть слот;
2. есть свободный номер ≤ лимита → занять;
3. иначе (панель приняла новое устройство, значит у неё список сбросили) → переназначить слот с самым старым `lastSeenAt`.
Гонку двух одновременных новых устройств гасят уникальные индексы: при конфликте транзакция повторяется один раз.
Альтернатива из `incy_merge.py` — сверять с реальным списком HWID панели — недоступна без её БД; отставание от сброса на панели мы закрываем шагом 3.

### 5. Вспомогательный клиент слота 2 создаётся заранее, не в запросе
`<panelEmail>-AWG2`, случайный скрытый `subId`, `limitHwid: 0` (его запрашивает только наш сервер), привязан только к AmneziaWG-inbound. Создаётся вместе с профилем (`getOrCreateProfile`) и разовым бэкфиллом для существующих; `panelEmail`/`subId` вспомогательного клиента храним в `VpnProfile` (новые nullable-поля). Если на момент запроса его нет — AmneziaWG для слота 2 не выдаётся (лог), подписка работает.
Альтернатива — ленивое создание при первом запросе со второго устройства — отвергнута: запись на панель в горячем пути публичного эндпоинта, гонки двух запросов и сложнее гарантировать отзыв.

### 6. Порядок обработки запроса INCY
1. Как сейчас: проксируем основной запрос (JSON), при ошибке панели отдаём её ответ как есть.
2. Если User-Agent — INCY, ответ 200 и есть `X-HWID` ≥ 6 символов, а профиль найден: слот → subId слота → сырая подписка → конфиги AWG → `AllowedIPs` → дописываем элемент `amneziawg` в JSON-массив (если тело — объект, оборачиваем в массив, как `subJsonAlwaysArray`).
3. Любое исключение шага 2 — лог (без HWID и ключей) и ответ из шага 1.
Весь шаг 2 закрыт флагом `config.vpn.awgEnabled` (`VPN_AWG_ENABLED`, по умолчанию `false`) — включаем после проверки на реальном устройстве.

### 7. Добавление inbound'а существующим клиентам — через API панели
Бэкфилл — идемпотентный скрипт (`apps/api/src/scripts/`), запускается вручную: для каждого активного `VpnProfile` добавляет AmneziaWG-inbound основному клиенту и создаёт вспомогательного, если его нет. Точный эндпоинт привязки существующего клиента к inbound'у (`clients/update` с `inboundIds` или аналог) проверяется первой задачей реализации на тестовом клиенте.

## Risks / Trade-offs

- [Укрупнение до /19 отправляет часть не-российских адресов напрямую] → осознанный компромисс ради лимита iOS; Telegram и корпоративный прокси-адрес принудительно возвращаются в туннель.
- [Сырой запрос слота 1 с тем же `X-HWID` — второй запрос к панели на одно обновление подписки] → устройство уже зарегистрировано первым запросом, лимит не тратится; задержка +1 запрос к панели только для INCY.
- [Скрытый `subId` вспомогательного клиента без лимита устройств — если утечёт, ключ слота 2 можно использовать] → subId никогда не покидает сервер (сотруднику отдаётся только основной), удаляется при увольнении.
- [Сброс HWID на панели не виден нам сразу] → старые слоты переназначаются по `lastSeenAt` только когда панель уже приняла новое устройство.
- [Формат `vpn://` и JSON — внутренности конкретной сборки панели] → строгая проверка формата, любая неожиданность = подписка без AmneziaWG, а не поломка.
- [Размер ответа INCY растёт на ~150–200 КБ на конфиг] → приемлемо, подписка обновляется раз в 12 ч.
- [Константы корпоративных адресов расходятся с Routing-профилем панели, если его поменяют] → комментарий-источник у констант; расхождение затрагивает только AmneziaWG.

## Migration Plan

1. Prisma-миграция (`VpnAwgSlot`, новые поля `VpnProfile`) — аддитивная, откат не требуется.
2. Деплой с `VPN_AWG_ENABLED=false` — поведение не меняется; новые профили уже получают inbound `915` и вспомогательного клиента.
3. Бэкфилл существующих профилей скриптом.
4. На панели: включить `subIncyEnableRouting` с профилем «RU напрямую» (как `subRoutingRules`).
5. `VPN_AWG_ENABLED=true`, проверка на реальных двух устройствах в INCY (разные ключи, RU-сайт напрямую, Telegram через VPN).
Откат: `VPN_AWG_ENABLED=false` — INCY снова получает только Xray; привязка inbound'а и вспомогательные клиенты не мешают.
